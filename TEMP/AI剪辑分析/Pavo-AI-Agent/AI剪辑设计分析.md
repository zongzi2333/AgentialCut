# Pavo AI Agent：AI 剪辑架构分析

## 架构判断

**Pavo 不属于典型 ReAct，也不属于完整的 Plan-Action。最准确的归类是：固定工作流驱动的多角色生成流水线。**

如果只允许在两者之间选择，它更接近 **Plan-Action 一侧的预设计划执行**：执行顺序提前写好，系统按顺序调用 AI。但计划来自程序，模型生成的规划并没有控制后续执行。

本文的 ReAct 指 Reasoning + Acting，即“推理 → 行动 → 观察结果 → 再推理”，与 React 前端框架无关。

## 判断依据：谁决定下一步

| 判断点 | Pavo 的实际做法 | 架构含义 |
| --- | --- | --- |
| 阶段顺序由谁决定 | 服务端固定顺序 | 工作流控制，不是 Agent 自主选择 |
| Planner 是否生成可执行计划 | 生成故事要素；结果未用于调度后续阶段 | 有规划角色，但没有计划执行器 |
| 模型是否选择工具 | 内部生成 Agent 不选择工具 | 缺少 ReAct 的行动决策 |
| 执行结果是否回填模型 | 后一个角色接收前面的内容 | 属于阶段数据传递，不是同一 Agent 的观察循环 |
| 审核后是否持续迭代 | 审核一次，必要时修复一次 | 有限质量反馈，不是开放式循环 |

因此，“有 Planner”不足以认定 Plan-Action，“有 Reviewer”也不足以认定 ReAct。

## 一次任务如何运行

用户提交故事后，服务端依次调用故事分析、角色设计、场景设计、道具设计、分镜生成。每个角色通常只做一次模型调用，输出结构化内容，交给后面的阶段使用。

分镜生成后，审核角色检查人物、场景、动作连续性和时长分配；需要修复时，再调用修复角色重写分镜。修复之后没有再审核直到通过的循环。

**控制关系是：程序决定做什么，模型完成这一项内容生成。** 模型不能自行决定先查素材、试剪一版、观察效果，再选择下一项操作。

## “规划”为什么没有形成 Plan-Action

真正的 Plan-Action 至少需要“计划产物 → 执行器”的连接：计划定义任务、依赖、目标或验收条件，执行器据此选择动作。

Pavo 的故事分析虽然输出角色、场景、主题、情绪和建议时长，但主流程随后仍按固定顺序调用各个角色；这个分析结果也没有作为后续生成的显式输入。它更像一次前置分析，并没有成为整个制作过程的控制依据。

这会造成一个结构性问题：**分析、生成和媒体执行之间没有统一的计划约束。** 即便规划给了时长建议，后面的分镜和视频生成也没有形成围绕该计划验证、调整的闭环。

## AI 到底操作什么

AI 主要操作的是角色、场景、道具、分镜这些内容文档。分镜描述景别、运镜、动作、台词和时长，表达的是“希望拍到什么”。

生成视频时，系统将分镜内容拼成提示词，逐镜调用视频模型，得到片段列表。当前主链路没有把这些片段进一步变成包含裁剪、转场、字幕、混音的最终成片。

所以它缺少剪辑架构中的关键中间层：**把“镜头描述”转换成“素材入出点、播放顺序、音画时间关系”的剪辑决策。** 人工调整分镜顺序和时长，也不等于 AI 执行了视频剪辑。

## 反馈与记忆的实际边界

质量反馈主要针对文本，而不是生成后的真实画面。审核输入还被截断，结构校验存在保留原始数据的宽松回退；审核回复无法识别时，默认按通过处理。因此审核层提供的是辅助判断，不能视为严格的质量闸门。

记忆中间层会在 MCP 请求中加入历史记忆，但项目调度主要提取故事、用户和模块参数，未将这些记忆继续传给内部生成 Agent。知识库检索也没有接入七角色主流程。**具备记忆模块，不代表生成决策已经受记忆驱动。**

外部 AI 可以通过 MCP 选择“创建、查询、重生成、生成视频”等项目动作。外部客户端可能采用 ReAct，但这不会改变 Pavo 内部仍是固定流水线的事实。

## 最终定位

**主架构：固定工作流；内部节点：单次模型生成；局部反馈：一次审核与可选修复。**

它适合把故事快速变成分镜草案。要演进为 Plan-Action，需要让规划真正约束后续任务；要演进为 ReAct，需要增加可调用的剪辑动作，并把素材分析、试剪、画面检查的真实结果送回模型，让模型据此决定下一步。
